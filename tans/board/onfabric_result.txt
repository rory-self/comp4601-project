On-fabric result -- tree method (static tANS), KV260 PL @ 200 MHz, K=4 SIMD + 64-bit AXI
Workload: 4 files (32 KB each) SHARING ONE frequency table; the table is precomputed
once from that shared distribution and baked into the kernel. This is the workload
class the tree method targets.

Software baseline = the SAME efficient byte-packing tANS encoder on the ARM
(NOT the tans.h BitStack reference, which does a vector push_back per bit and
would have inflated the speedup ~3x -- 18.2 M/s instead of the true 56.3 M/s).

  file0: 32768 B  LOSSLESS  ratio 84.00%   ARM 56.11 M sym/s | FPGA 149.61 M sym/s  2.67x
  file1: 32768 B  LOSSLESS  ratio 84.15%   ARM 56.26 M sym/s | FPGA 147.14 M sym/s  2.62x
  file2: 32768 B  LOSSLESS  ratio 84.06%   ARM 56.32 M sym/s | FPGA 147.05 M sym/s  2.61x
  file3: 32768 B  LOSSLESS  ratio 84.12%   ARM 56.32 M sym/s | FPGA 147.71 M sym/s  2.62x

  TOTAL 131072 B -> 110206 B (84.08%, == the source entropy: the static table is
  optimal for this workload class)
  lossless : YES (the board's output was decoded on the host and matched the input)
  ARM      : 2330.2 us  =  56.25 M sym/s
  FPGA     :  886.4 us  = 147.87 M sym/s
  SPEEDUP  : 2.63x

Cosim predicted 194 M/s (kernel only); fabric gives 147.9 M/s. The ~24 us/call XRT
overhead at 16 KB blocks accounts for the gap -- i.e. calculated vs actual differ by
the host interface, not by the kernel (spec step 7b).

How it got here (each step removed a HARDWARE blocker, not an algorithm change):
   28.2 M/s   K-way, shared table ROM        -> lanes serialised (1 read port)
   35.8 M/s   SIMD lockstep + per-lane tables -> lanes actually parallel (II=2)
  194.0 M/s   + 64-bit aligned AXI            -> I/O was 90% of runtime
  147.9 M/s   on real fabric                  -> minus XRT per-call overhead

=================== MULTI-INSTANCE (2 compute units) ===================
One kernel used only ~16% LUT / 34% BRAM, so the chip was mostly idle. Rebuilt
with nk=arith_kernel:2, each CU on its OWN HP port pair (CU1 -> HP0/HP1,
CU2 -> HP2/HP3) so they do not contend for AXI bandwidth. Same bitstream holds
both CUs, so running 1 vs 2 isolates the effect.

  1 CU  : 111.6 us/call   146.75 M sym/s   lossless=YES
  2 CUs : 114.3 us/pair   286.65 M sym/s   lossless=YES
  scaling: 1.95x  (2.00x = perfect)

  vs the ARM software baseline (56.25 M sym/s):  2.61x -> 5.10x

Near-linear, so neither DDR bandwidth nor XRT dispatch was a limit at this rate.
This was the single largest win available: we had been optimising one kernel while
two thirds of the fabric sat unused. BRAM (34%/CU, from the per-lane table copies)
caps this at 2 CUs; a smaller table or fewer lanes per CU would allow more.
